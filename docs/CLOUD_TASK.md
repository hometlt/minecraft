# Задание для облачного агента: доработка StarMine

Документ — постановка задачи для агента, который работает с репозиторием
https://github.com/hometlt/minecraft в облаке (без доступа к машине владельца). Его нужно прочитать
целиком до первой правки. Отчёты владельцу — **на русском**.

Цель: довести мод до состояния, описанного в `README.md`:
1. реализовать **все способности и механики** из `docs/ABILITIES.md` для всех юнитов трёх рас;
2. **протестировать и починить поиск пути** — юнитов, рабочих, армий, летунов, транспорта;
3. **сбалансировать расы** между собой (бой, экономика, ИИ).

---

## 1. С чего начать

1. Прочитать `README.md` (что такое мод), `docs/ARCHITECTURE.md` (устройство кода, принципы),
   `docs/ABILITIES.md` (план способностей с приоритетами), затем по необходимости
   `docs/HIVE_DESIGN.md`, `docs/TERRAN_DESIGN.md`, `docs/VESPENE_DESIGN.md`.
2. Собрать и прогнать тесты, убедиться, что исходное состояние зелёное:

   ```bash
   chmod +x gradlew
   ./gradlew compileJava compileClientJava
   ./gradlew runGametest
   ```

   Результат — `build/gametest/junit.xml`; сейчас там **38 тестов, все проходят**. Если что-то красное
   на чистом `main` — сначала зафиксировать это в отчёте, а не «чинить заодно».

### Окружение облака

- Нужна **Java 21**; Gradle и зависимости (Minecraft 1.21.1, Fabric Loader 0.19.5, Fabric API
  0.116.17, Loom) скачиваются при первой сборке — нужен доступ в интернет к Maven Fabric и Mojang.
- **Ассетов StarCraft II в облаке нет и не будет.** Каталог `sc2-assets/` не хранится в git; без него
  мод собирается и работает, юниты рисуются контурами. Для тестов на сервере это не важно.
- **Клиента Minecraft в облаке нет.** Клиентский код (`src/client`) можно только компилировать
  (`compileClientJava`). Всё, что проверяется, проверяется **игровыми тестами на сервере**
  (`runGametest`, Fabric GameTest, арена `starmine:arena` 48×48×12). Что требует глаз (интерфейс,
  модели, частицы), перечислить в отчёте как «проверить владельцу в игре».

## 2. Обязательные правила

- **Никаких ассетов Blizzard** (модели, текстуры, звуки, значки, тексты из игры) в репозитории — ни в
  коде, ни в тестах, ни в ресурсах. Цифры SC2 (здоровье, урон, время, стоимость, дальность) —
  можно: это факты; источник — данные мультиплеера LotV (например, вики по SC2).
- **Не копировать код сторонних модов и проектов** (в том числе модов Minecraft с похожими
  механиками и любых GPL/LGPL-проектов). Лицензия StarMine — MIT. Сторонние проекты в документах и
  README **не упоминать**.
- Работать **в отдельной ветке** (`cloud/<тема>`) и открывать pull request в `main`. Не делать
  force-push в `main`, не переписывать историю.
- Коммиты — небольшие, по одной теме, сообщение объясняет *зачем*; в конце строка
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Перед каждым коммитом:
  `compileJava compileClientJava` и `runGametest` зелёные.
- Каждая новая механика — с **игровым тестом**, который падает без неё. Тест, проверяющий только
  то, что код вызвался, не считается.
- Код — Java 21, стиль соседнего кода: табы, комментарии-javadoc у классов и методов о том, *что* и
  *зачем*, без пересказа кода. Документация и сообщения в игре — двуязычные `en_us.json` и `ru_ru.json`.
- **Принципы архитектуры** (`docs/ARCHITECTURE.md`): кто кому враг — только `faction/Faction`; всё,
  чем отличаются расы, — в правилах расы (`race/*Race.java`), а не в `if (terran)` в общем коде;
  цифры юнита — в `UnitKind`; одна база игрока на измерение. Новая способность: константа в
  `ability/Ability.java` (цифры), пользователи в `users()`, эффект — в классе своей расы
  (`ZergAbilities`, `TerranAbilities`, `ProtossAbilities`) или общей механике, вызов — из
  `Abilities.effect`, затем добавить её в `Abilities.READY`.

## 4. Задачи

Порядок — по этапам; внутри этапа сначала приоритет 1 из `docs/ABILITIES.md`.

### Этап A. Общая основа для оставшихся способностей

1. **Временные состояния юнита** (одно место, например `ability/Status`): стимулятор, замедление,
   обездвиживание, ослепление (ближний радиус стрельбы), защитное поле (−урон дальних атак),
   подъём (гравитонный луч), ускорение времени здания, барьер бессмертного. С истечением, сохранением в
   NBT и пересчётом оружия и скорости (`StarUnit.applyWeapon`, модификаторы атрибутов). Для игрока,
   управляющего юнитом, — то же на его теле (`Possession.updateSpeed` и атрибуты).
2. **Режимы шире осады**: полёт ↔ земля (посадка викинга — смена навигации и управления движением,
   `noGravity`), геллион ↔ геллбат (оружие, здоровье, «биологический»), закапывание (невидимость без
   энергии, неподвижность, кроме таракана), режим фазы призмы (неподвижна, даёт энергию как пилон —
   `ProtossRace.poweredAt`), орбитальная станция / планетарная крепость (смена режима здания).
3. **Пассивные эффекты** — хуки в одном месте: при нанесении удара (сотрясающие снаряды), при
   получении урона (барьер, защитное поле), каждый тик (батарея щитов, маскировочное поле
   материнского корабля, перехватчики авианосца, атака скрытня только закопанным).
4. **Способности зданий** в карточке команд (слоты 11–13 уже выводятся) и **ИИ** для них.
5. **Ресурсные способности** (ремонт за минералы, MULE): стоимость берётся из базы через уже
   существующие поля `Ability.minerals/vespene` или поминутно — описать решение в javadoc.

Критерий: каждая механика — свой тест; все прежние тесты зелёные.

### Этап B. Способности приоритета 1

Зерги: закапывание (и атака скрытня только закопанным), едкая желчь, грибковое разрастание,
обнаружение надзирателем закопанных. Терраны: стимулятор, сотрясающие снаряды, прыжки жнеца по
уступам (проверить, что уже работает высота шага 2), ЭМИ, посадка викинга, перевозка медэваком
(есть), ремонт КСМ. Протоссы: рывок фанатика, скачок сталкера, силовое поле (временный блок, который
сам исчезает через запланированный тик блока — не через память сервера), псионический шторм,
слияние двух храмовников в архонта, гравитонный луч феникса, пульсирующий луч оракула (оружие только
при включённом), перехватчики авианосца, восстановление щитов батареей.

Для каждой способности:
- эффект с цифрами SC2 (перевод: урон и здоровье ×10/35 — `UnitKind.SCALE`, дальность ×1,153 + 1
  блок, время — реальные секунды LotV);
- правило в `AbilityAi` для диких юнитов (когда применять, когда выключать);
- тест: юнит применяет, эффект виден в состоянии мира (урон, позиция, блоки, состояние цели), отказ
  при нехватке энергии/здоровья/перезарядке;
- для способностей с прицелом — проверка «подойти и применить» из командного интерфейса
  (`Abilities.order`) и применение модулем, управляя юнитом.

### Этап C. Способности приоритета 2 и 3

Все оставшиеся из `docs/ABILITIES.md`, с теми же требованиями. Упрощения, перечисленные в
разделе «Упрощения» того документа, — разрешены (ядерный удар разрушает блоки только при отдельном
правиле игры, по умолчанию выключенном; нейронный паразит — временное переподчинение). Когда всё
сделано, список `Abilities.READY` и отказ «пока не готово» удаляются.

### Этап D. Поиск пути — тесты и исправления

Сделать набор игровых тестов поиска пути (отдельный класс, например
`entity/PathfindingGameTests`) и починить то, что они найдут. Сценарии:

| Сценарий | Кто | Ожидание |
| --- | --- | --- |
| Ровное поле, 30 блоков | все наземные размеры (зерглинг 0,8 — ультралиск 2,8 — тор 5) | доходят до точки приказа |
| Стена 3 блока, проход шириной 1 / 2 / 3 | разные размеры | маленькие проходят, крупные ищут обход или ждут прокладки пути |
| Обрыв 4 блока вверх и вниз | наземные, жнец, колосс | жнец и колосс поднимаются, остальные идут в обход или рабочие режут ступени |
| Река шириной 5 и 12 | наземные, армия с рабочими | рабочие строят мост (`colony/Engineering`), армия проходит |
| Гора без прохода | армия с рабочими | рабочие прорубают туннель под самый крупный юнит армии |
| Пещера, туннели логова | зерги | ходят по туннелям, не застревают в поворотах |
| Лес | наземные | не застревают в листве и стволах |
| Полёт над горой, под потолком, над водой | все летуны | держат высоту, долетают, не упираются в потолок |
| Транспорт через пропасть | медэвак, призма, повелитель | загрузка, перелёт, выгрузка на землю |
| Толпа 20+ юнитов в узком проходе | смешанная армия | все проходят за разумное время, без вечной толкотни |
| Здания на пути | все | обходят здания, не перелезают через них |
| Волна дикой базы на базу игрока за 100+ блоков | ИИ | волна доходит и атакует |

Мерить и записывать в отчёт: время до цели (тики), застрявших, число узлов поиска и время планирования
`DronePlanner` (бюджет на тик — не превышать). Известные особенности тестовой среды:
- карта высот считает **барьерный потолок арены** землёй — летунам в тестах нужно очищать барьеры над
  ареной (см. `AbilityGameTests.arena`);
- управление полётом (`FlyingMoveControl`) держит цель **один тик** — летуну цель нужно задавать каждый
  тик или через навигацию;
- **мок-игрок**, оставленный в мире, заставляет мобов других тестов исчезать (деспаун вдали от
  игрока) — убирать его в `finally` (см. `PossessionGameTests`);
- тестам с зергами улья — свой `batch` и `HiveSavedData.clear()`.

### Этап E. Баланс рас

1. **Стенд боёв**: игровой тест-«арена», где две армии **равной стоимости** (минералы + газ по ценам
   SC2) разных рас сражаются до победы. Набор составов: ранние (зерглинги / морпехи / фанатики),
   средние (тараканы+гидралиски / морпехи+мародёры+медэваки / сталкеры+часовые), поздние (с
   ультралисками, танками, колоссами, летунами). Прогонять каждый бой несколько раз с разными
   семенами, симметрично (стороны местами). Результат — таблица в `docs/BALANCE.md`: победы,
   оставшаяся стоимость армии победителя, длительность боя.
2. **Цель**: при равной стоимости и сопоставимом составе ни одна раса не выигрывает систематически
   (примерно 40–60 % побед в зеркальных по уровню технологий составах); «контры» SC2 сохраняются
   (например, гиблинги против морпехов, бессмертные против танков).
3. **Что можно менять**: цифры в `UnitKind` и правилах рас, но **осознанно** — каждое отклонение от
   цифр SC2 записать в `docs/BALANCE.md` с причиной (перевод в Minecraft искажает: ближний бой,
   толкотня, блоки, высота). Общую шкалу `UnitKind.SCALE` не менять без согласования с владельцем.
4. **Экономика и ИИ**: скорость добычи минералов и газа, время до первой волны дикой базы каждой расы,
   размер и состав волн (`ai/AiCommander`) — сравнить расы между собой, записать и выровнять.
5. **Игрок против диких баз**: насколько опасны волны для игрока без армии и с армией — описать.

### Этап F. Управление юнитом — доводка

Все способности работают модулями (тест на каждую расу); управление летуном (посадка викинга меняет
полёт игрока); транспорт, которым управляет игрок, — либо сделать загрузку в тело игрока, либо
явно отказать с сообщением; щиты и энергия на экране (клиент — только компиляция, описать для
проверки владельцем).

## 6. Чего не делать

- Не добавлять ассеты SC2, не скачивать игру, не писать загрузчики игровых архивов (этим занимается
  отдельный инструмент владельца, Modkit, вне этого репозитория).
- Не менять `build.gradle` так, чтобы публичная сборка начинала включать `sc2-assets`.
- Не переписывать работающие системы «с нуля» — расширять существующие классы.
- Не отключать и не ослаблять существующие тесты, чтобы стало зелено; если тест устарел — объяснить
  в коммите, почему меняется ожидание.
